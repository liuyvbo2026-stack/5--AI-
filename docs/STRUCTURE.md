# 仓库目录与负责区域

此结构服务于两个阶段：前 48 小时由组长独立开发；随后 2～3 周由七人团队迭代。A–F 是待绑定到具体组员的岗位代号。当前源码仍是旧故事原型，下面的“负责”表示**后续维护与交付边界**，不表示相应的新功能已经实现。

```text
5--AI-/
├── .github/       组长：任务模板、PR 规则、CI
├── web/           A：页面交互与前端集成；B：页面视觉与响应式
├── server/        D：真实生图接口；F：邀请码与业务校验
├── shared/        组长协调：前后端共用数据格式
├── tests/         各功能作者：本模块测试；C：整站回归与验收
├── design/        B：界面方案、素材来源与体验检查
├── photography/   E：三套摄影风格配置、提示词与效果评测
├── ops/           C：部署步骤、运行检查与交付记录
├── scripts/       C 维护部署相关脚本；旧人工导入脚本已移除
├── docs/          组长维护范围与计划；各角色维护本人交接文档
└── examples/      历史示例；不作为真实生图成功的证据
```

## 同一目录内的边界

| 路径 | 默认负责人 | 交接规则 |
| --- | --- | --- |
| `web/*.js` | A | 页面状态与接口调用由 A 集成；改 HTML 元素标识时先与 B 对齐。 |
| `web/index.html`、`web/styles.css`、`design/` | B | B 负责可落地的视觉方案、样式和手机适配；功能脚本改动请 A 审查。 |
| `server/` 中的生图调用 | D | 先做真实 API 验证；与 F 约定生成任务和邀请码状态的接口。 |
| `server/` 中的邀请码、输入校验和风格选择 | F | 先实现确定性的业务逻辑；照片分析、智能推荐排在核心流程稳定之后。 |
| `photography/` | E | 三套可执行配置与真实结果评测；提示词如何传给 D 先约定格式。 |
| `ops/`、部署配置 | C | C 负责部署与整站回归；各功能作者仍须自测并记录结果。 |
| `shared/`、`package.json`、`.github/` | 组长协调 | 涉及多位组员或全局构建的文件，改前在 Issue 说明影响，指定一人集成。 |

目前 `server/app.mjs` 等文件可能同时涉及 D 和 F。它们不能在两个 PR 中并行改同一段代码；先约定接口，由一人集成，另一人审查。目录映射是协作约定，不是 GitHub 权限设置，也不等于已配置 `CODEOWNERS`。

真实 API Key、邀请码明文、真人照片及生成结果不得提交到公开仓库。设计参考图和风格样例也须确认可使用，再放入仓库。
