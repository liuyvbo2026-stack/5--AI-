# 七人团队阶段任务池（接在组长 48 小时 MVP 之后）

本文件替代旧“回忆／三幕相册／人工交付”七人分工。前 48 小时由组长独立做五步 MVP；团队从**届时实际交付的代码、测试和未完成项**接手，不把下面的任务当作已经完成，也不要求组员重新搭一套网站。A–F 是岗位代号，实际用户名和可投入时间确认后再指派 GitHub Issue。

## 节奏

| 时段 | 集中完成的事 | 通过条件 |
| --- | --- | --- |
| 第 1 周：接手与稳定 | 复核五步流程、真实 API 权限、邀请码行为、部署位置；补当前阻断问题 | 能重现组长的真实演示，列出并认领阻断问题；不把旧故事代码算成进度。 |
| 第 2 周：质量与体验 | 页面与手机适配、三种风格质量、错误处理、自动测试、部署与回归 | 改进项通过 PR；三种风格与失败路径有实际验证结果。 |
| 第 3 周：按余量选做 | 评估照片质量分析、风格推荐、更多样式或框架迁移 | 先提出可验证收益、时间成本和隐私影响，再选一个小任务；核心五步持续可用。 |

两周内不把第三周可选项硬塞进开发。若组长的 48 小时版本尚未完成某个五步环节，第 1 周先补该阻断项，再排体验优化。

## 岗位任务卡

每张任务卡只是一个责任方向。真正开工时再拆为预计 2～4 小时、只有一位主负责人的 GitHub Issue；每项写清所改文件、前置依赖和验收证据。

岗位责任卡已建在仓库中：[组长 #21](https://github.com/liuyvbo2026-stack/5--AI-/issues/21)、[A #15](https://github.com/liuyvbo2026-stack/5--AI-/issues/15)、[B #16](https://github.com/liuyvbo2026-stack/5--AI-/issues/16)、[C #17](https://github.com/liuyvbo2026-stack/5--AI-/issues/17)、[D #18](https://github.com/liuyvbo2026-stack/5--AI-/issues/18)、[E #19](https://github.com/liuyvbo2026-stack/5--AI-/issues/19)、[F #20](https://github.com/liuyvbo2026-stack/5--AI-/issues/20)。A–F 均未指派真实账号；在前 48 小时 MVP 结束前保持计划状态。

| 岗位 | 第 1 周先做 | 第 2 周主要交付 | 第 3 周可选或支持 | 验收重点 |
| --- | --- | --- | --- | --- |
| 组长 | 发布基线版本、接口与未完成清单；确认 A–F 人选和时间 | 审 PR、解决共享文件冲突、每周完整验收 | 决定下一轮范围 | 有单一任务看板、合并记录与五步演示结果。 |
| A 前端 | 跑通现有页面，修复五步交互的阻断问题 | 上传／预览／更换、等待／失败、结果下载与前端集成 | 评估是否需要 Next.js | 真正连接服务端；手机上也能完成五步。 |
| B 设计 | 检查当前页面和五步操作，交付可实现的视觉与文案清单 | 提交页面样式、手机布局和状态反馈的 PR | 用户试用与视觉细节 | 不只交图片稿；实际网页易看、易懂、可操作。 |

## 协作边界

- A 与 B 先约定页面元素和状态；D 与 E 先约定风格配置格式；D 与 F 先约定生成任务与邀请码状态。约定写在相关 Issue 或 `docs/`，再并行实现。
- `server/app.mjs`、`shared/contract.mjs`、`package.json` 等共享文件由组长指定一人集成，其他人先提需求或审查，不在两个 PR 中各自大改。
- 每位作者写本功能的检查和 PR 验证步骤；C 执行整站回归；组长最终验收并决定合并。
- 真实 API Key、邀请码明文、真人照片、生成结果与访问凭据不进公开仓库、Issue 和 PR。
